L'entrée de 07:35 donnait, comme marche à suivre, `gdrive-sync check` en

laissé passer une panne silencieuse.**

vérifie pas que la valeur qu'il contient **déchiffre `rclone.conf`**. Il

**Le geste a deux moitiés, et elles se sont désolidarisées le 15/09 :**

1. `gdrive-sync set-password` → **faite**. Le trousseau a reçu une valeur
   neuve.
2. `rclone config` → `s` → `c` → **oubliée**. `rclone.conf` est resté
   chiffré avec l'ancienne.

Résultat : trousseau et config désaccordés, moteur cassé, **et `check`
qui continuait à dire que tout allait bien**. Le mtime de `rclone.conf`
le trahissait déjà — inchangé à `07:12:54`, alors qu'un changement de mot
de passe réécrit le fichier.

**Les deux vérifications qui font foi :**

```
    → doit afficher gdrive: et gdrive2:

stat -c '%y' ~/.config/rclone/rclone.conf
    → le mtime doit avoir bougé au moment du changement
```

**Séquence corrigée, dans cet ordre :**

```
1. rclone config → s) Set configuration password → c) Change Password

2. gdrive-sync set-password           (la MÊME valeur neuve)
3. RCLONE_CONFIG_PASS=<trousseau> rclone listremotes    ← la vraie vérification
4. gdrive-sync check                  (confort, ne prouve rien à lui seul)
```

### La réparation — méthode non interactive

`rclone config` est une TUI et le shell de Claude Code n'est pas un vrai
terminal. Deux contournements, tous deux documentés pour la prochaine
fois :

- **`rclone config encryption set --password-command <script>`.** rclone
  appelle le script **deux fois** : une première pour déchiffrer avec
  l'ancienne, une seconde avec `RCLONE_PASSWORD_CHANGE=1` dans
  l'environnement pour lire la nouvelle. Entièrement non interactif.
- **Côté trousseau**, `gdrive-sync set-password` passe par
  `getpass.getpass`, donc inutilisable sans terminal : on appelle
  directement `gdsync.secret.store_in_keyring(cfg.keyring_label, valeur)`,
  ce que la sous-commande fait par-dessous.
